# CDN Tunnel

Туннель TCP/UDP-трафика через CDN: один Go-файл (сервер + клиент) и
Android-приложение (VPN на весь телефон, автодеплой сервера, панель управления).

Клиент поднимает локальный **SOCKS5**; трафик идёт через CDN (TLS+HTTP/2, SNI),
реальные исходящие коннекты делает сервер (исходящий IP = IP сервера).
Вниз — длинный потоковый ответ, вверх — chunked-запросы (или потоковый `stream`).

```
Телефон/ПК ──TLS+HTTP/2──► CDN (ip:443, SNI=host) ──HTTP:80──► ваш сервер ──► интернет
```

## Быстрый старт: свой VPN за 5 минут

**Что нужно:** VPS с Linux и root-доступом по SSH, домен за CDN (Cloudflare и
подобные), у которого origin — этот VPS, и Android-телефон.

1. **Поставьте приложение.** Скачайте `cdn-tunnel.apk` из
   [Releases](../../releases), разрешите установку из неизвестных источников.
2. **Разверните сервер.** Вкладка **«Сервер»**: адрес VPS, SSH-порт,
   пользователь (`root`), SSH-пароль. Поле **«Мастер-ключ сервера»** оставьте
   пустым — он сгенерируется сам. Нажмите **«Развернуть»**: приложение зальёт
   бинарь в `/usr/local/bin/cdn-tunnel`, пропишет systemd-юнит с автозапуском
   и запустит его.
3. **Подключитесь сами.** Вкладка **«Туннель»** → «Ручная настройка»: IP CDN,
   Host/SNI и тот же мастер-ключ в поле «Мастер-ключ (вход без ссылки)» →
   **«Запустить VPN»**. Владельцу ссылка не нужна — он входит по ключу.
4. **Позовите друга.** Вкладка «Сервер» → **«Управление сервером»** →
   **«Новая ссылка»**: введите Host/SNI и IP CDN, подпишите («Андрею») и
   отправьте полученную `cdn://…` в мессенджер. Друг ставит тот же APK,
   открывает ссылку (или вставляет её на вкладке «Туннель» → «Импортировать»)
   и жмёт «Запустить VPN». Пароль ему не нужен.

Ссылка **привязывается к первому устройству**, которое по ней подключилось:
со второго телефона она уже не откроется. Отвязать, отозвать или удалить любую
ссылку можно в «Управлении сервером» — **удалённая ссылка не работает больше
никогда**, даже если клиент переподключится.

---

## Кто чем управляет

| Роль | Что видит и может |
|------|-------------------|
| **Владелец** (мастер-ключ) | панель: все выпущенные ссылки, их трафик, устройство и состояние; выпустить, отвязать, сбросить с линии, отозвать, удалить; перезапуск и обновление сервера; прямой вход без ссылки |
| **Друг** (ссылка) | только подключение по своей ссылке |

Мастер-ключ друзьям не передаётся: ссылка несёт лишь своё удостоверение,
подписанное этим ключом (подробности ниже).

**Никаких «пользователей» нет.** Единица доступа — ссылка: одна ссылка = один
человек = одно устройство. Хотите пустить ещё кого-то — выпустите ещё ссылку;
хотите отрезать — удалите её.

## Сервер (origin, за CDN)
```bash
./tunnel -server -addr :80 -password 123456 -method both
```
`-password` — **мастер-ключ**: им подписываются ссылки, им открывается панель
`/admin`, по нему владелец заходит напрямую. Без него ссылки выпускать нечем.

Подключиться к серверу можно ровно двумя способами: мастер-ключом (владелец) или
ссылкой, **которая есть в реестре сервера и не отозвана**. Всё остальное — 403.
Реестр лежит в файле `-state` (по умолчанию `/var/lib/cdn-tunnel/links.json`) и
переживает перезапуск вместе со счётчиками трафика и привязками к устройствам.

Клиент считается «на линии», пока пингует сервер (раз в 15 с). Молчание дольше
45 секунд или запрос `/bye` (по Ctrl-C / SIGTERM) снимает его с линии.

## Клиент (локальный SOCKS5)
```bash
# владелец — по мастер-ключу:
./tunnel -client -ip <CDN_IP> -host <cdn.domain> -password 123456 -listen 127.0.0.1:8090
# друг — по ссылке:
./tunnel -client -link "cdn://AYutF0…" -listen 127.0.0.1:8090
# затем: curl --socks5-hostname 127.0.0.1:8090 https://api.ipify.org
```

## Ссылка cdn:// (поделиться настройками)
```bash
# собрать ссылку из текущих параметров:
./tunnel -share -ip <CDN_IP> -host <cdn.domain> -password 123456
cdn://AYutF0ZIlOWh-DylEfgZumfC3J3i5MEhm05TYXNIC_bN…  (пример)

# подключиться по ссылке (перекрывает -ip/-host/-password/-conns/-method/-transport):
./tunnel -client -link "cdn://AYutF0…"
```
В ссылке **нет мастер-пароля**: она несёт собственное удостоверение
`<id>.<подпись>` (HMAC-SHA256 от `-password` сервера). Подпись доказывает, что
ссылку выпускал владелец этого сервера, но **доступ даёт не подпись, а запись в
реестре**: ссылки, которой в реестре нет, для сервера не существует.

Ссылка **привязывается к первому устройству**, которое по ней подключилось
(`-device`, по умолчанию хеш `/etc/machine-id`). Второму устройству с той же
ссылкой — `409` и «ссылка занята»:

```bash
./tunnel -client -link "cdn://…"      # первое устройство: работает
./tunnel -client -link "cdn://…"      # другое устройство: ✗ ссылка занята
```
Снять привязку: `/admin/link/unbind` (см. ниже) или кнопка «Отвязать» в приложении.

Что делает владелец в панели и что видит друг:

| Действие владельца | Что происходит с ссылкой |
|--------------------|--------------------------|
| **Сбросить** | клиента снимает с линии, ссылка рабочая — он тут же переподключится |
| **Отвязать** | забывает устройство: ссылку можно открыть на другом телефоне |
| **Отозвать** | доступ закрыт, запись и счётчики целы; **Вернуть** — снова работает |
| **Удалить** | запись стёрта, доступ закрыт **навсегда** — переподключение не поможет |

Содержимое зашифровано **AES-256-GCM** (ключ = SHA-256 общего секрета, nonce
случайный, версия формата в AAD), поэтому глазами в ссылке ничего не прочитать
и base64-декод ничего не даёт. Ключ одинаков во всех сборках — иначе получатель
не расшифровал бы ссылку, — так что это стойкая обфускация, а не тайна от того,
у кого есть бинарник: доступ решает пароль туннеля внутри ссылки. Тот же формат
понимает Android-приложение (вкладка «Ссылка» и открытие `cdn://…` из мессенджера).

## Панель сервера (`/admin`)
Только с мастер-ключом (`X-Tunnel-Auth`), удостоверением ссылки не открывается.
Приложение ходит в неё по SSH через `curl` на localhost, наружу светить не нужно.

| Ручка | Что делает |
|-------|-----------|
| `GET /admin` | снимок: версия, аптайм, сколько ссылок на линии, трафик сервера и весь реестр ссылок |
| `GET /admin/link/new?label=Андрею` | **выпустить ссылку**: сервер заносит её в реестр и возвращает `{id, cred}` |
| `GET /admin/link/kick?id=…` | снять клиента с линии (ссылка остаётся рабочей) |
| `GET /admin/link/unbind?id=…` | отвязать от устройства; `?all=1` — сразу все |
| `GET /admin/link/revoke?id=…` / `restore` | отозвать ссылку (клиент получает 403) / вернуть |
| `GET /admin/link/delete?id=…` | **удалить запись** — доступ по ссылке закрыт навсегда |
| `GET /admin/link/rename?id=…&label=…` | сменить подпись |

```bash
curl -s -H "X-Tunnel-Auth: мастер" http://127.0.0.1/admin | jq .
curl -s -H "X-Tunnel-Auth: мастер" "http://127.0.0.1/admin/link/new?label=Андрею"
```
Трафик считается **по каждой ссылке** (↓/↑ за всё время) и переживает перезапуск —
лежит в файле `-state` вместе с реестром. Владелец видит и ни разу не
использованные ссылки, и может закрыть любую.

## Ключевые флаги
| Флаг | Назначение |
|------|-----------|
| `-password` | мастер-ключ сервера (заголовок `X-Tunnel-Auth`, сверка в постоянное время; пусто = сервер открыт всем) |
| `-method` | клиент: `post`\|`get`; сервер: `post`\|`get`\|`both` (что принимать) |
| `-transport` | `chunked` (любой CDN) \| `stream` (один потоковый POST вверх, ниже пинг; при буферизующем CDN — авто-откат на chunked) |
| `-fastopen` | оптимистичный SOCKS-ответ (−1 RTT на соединение) |
| `-conns` | число TCP/h2-соединений к CDN (пул) |
| `-udp` | UDP ASSOCIATE (DNS/QUIC/прочий UDP) |
| `-window` | окно up-запросов в полёте (chunked) |
| `-idle` | таймаут простоя стрима на сервере, сек |
| `-state` | сервер: файл реестра ссылок (по умолч. `/var/lib/cdn-tunnel/links.json`) |
| `-link` | клиент: подключиться по ссылке `cdn://…` |
| `-cred` | клиент: удостоверение ссылки `<id>.<подпись>` без самой ссылки |
| `-device` | отпечаток устройства для привязки ссылки (по умолчанию сам) |
| `-share` | напечатать ссылку `cdn://…` с текущими настройками и выйти |
| `-stats` | машиночитаемый вывод `STATS ...` (для Android-обёртки) |
| `-require-e2e` | сервер: принимать только клиентов со сквозным шифрованием (нужен `-password`); остальным — 404 |
| `-legacy` | клиент: без сквозного шифрования (совместимость со старым сервером; ключ/ссылка идут в заголовках) |
| `-tls-fingerprint` | клиент: TLS-отпечаток к CDN — `chrome` (по умолч.), `firefox`, `safari`, `ios`, `edge`, `android`, `random`, `go` (обычный TLS Go, старое поведение) |
| `-allow-private` | сервер: разрешить ссылкам ходить в loopback/частные сети сервера (по умолчанию только владельцу) |
| `-admin-remote` | сервер: пускать `/admin` не только с localhost |

## Зачем серверу `-password`, если есть ссылки
`-password` — это **мастер-ключ сервера**, а не «ещё один пароль для друга»:
- им подписываются удостоверения ссылок (`<id>.<подпись>` = HMAC мастер-ключа),
  поэтому сервер проверяет любую ссылку, ничего о ней заранее не зная;
- им открывается админка `/admin*` (удостоверением ссылки — нет);
- по нему владелец подключается напрямую, без ссылки и без привязки к устройству;
- им открывается панель `/admin*` (удостоверением ссылки — нет).

Друзья мастер-ключ не видят и не вводят: у них только ссылка, привязанная к их
устройству и закрываемая в один тап. Без `-password` ссылки выпускать нечем, а сам
сервер открыт любому, кто знает домен CDN.

## Транспорт и безопасность
- TLS есть только на участке **клиент → CDN**; CDN → origin — обычный HTTP:80.
  Поэтому поверх HTTP работает **сквозное шифрование клиент↔origin** (по умолчанию
  у клиента): CDN видит только шифртекст, а мастер-ключ и ссылка по сети вообще не
  ходят.
  - Рукопожатие: эфемерный X25519 + общий секрет (PSK), который не покидает
    устройство: у владельца он выводится из `-password` (PBKDF2), у ссылки — из её
    подписи. Ключи `c2s`/`s2c` = HKDF(X25519 ‖ PSK, транскрипт): forward secrecy и
    взаимная аутентификация. Метка времени + одноразовый nonce защищают от повтора;
    часы клиента не должны расходиться с сервером больше чем на 2 минуты.
  - Данные: AES-256-GCM, у каждого стрима и направления свой подключ; в nonce
    счётчик (seq чанка / номер записи), поэтому подмена, перестановка и повтор
    записей отбрасываются.
  - Слабый `-password` можно перебирать офлайн по записанному рукопожатию — берите
    длинный случайный ключ. Ссылки (128-битная подпись) от этого не страдают.
  - Сервер по умолчанию принимает и старых клиентов (без E2E); чтобы закрыть их,
    запустите сервер с `-require-e2e`. Без `-password` E2E невозможно.
  - Сессия живёт, пока клиент активен (15 минут простоя); после рестарта сервера
    клиент договаривается заново, открытые в тот момент соединения рвутся.
- Доступ решает одна проверка: мастер-ключ владельца либо ссылка из реестра.
  Без верного ключа/подписи сервер отвечает **404** как обычный сайт; любой путь,
  кроме `/`, закрыт. Перебор ключа банит адрес на 15 минут.
- TLS-отпечаток клиента к CDN маскируется под настоящий браузер (uTLS,
  `-tls-fingerprint`, по умолчанию Chrome): порядок расширений, наборов шифров
  и кривых в ClientHello — как у реального Chrome, а не характерный для
  Go-клиента. Один раз при старте согласуется ALPN (h2/http-1.1) — дальше все
  соединения пула используют этот же протокол, каждое со своим TLS-рукопожатием
  тем же отпечатком. Это отдельный от сквозного шифрования слой: uTLS прячет
  форму TLS-рукопожатия от DPI/WAF перед CDN, а сквозное шифрование прячет
  содержимое от самого CDN. Если проба отпечатка не удалась (редкая
  несовместимость с конкретным CDN/сервером) — клиент один раз предупреждает и
  тихо откатывается на обычный TLS Go, чтобы соединение вообще заработало.
- Реестр авторитетен: удалённая ссылка мертва навсегда, отозванная — до «Вернуть».
  Подписи удостоверения самой по себе недостаточно.
- Ссылка `cdn://…` шифрует конфиг, но не заменяет пароль: у кого ссылка — у того
  доступ к серверу, пока владелец её не закрыл. Делитесь ей осторожно.
- `stream`/WebSocket-полнодуплекс требует CDN, не буферизующего тело запроса.
- Скачивание вниз переживает обрыв долгого GET (частое дело у буферизующих
  CDN/с таймаутом): сервер держит последние ~4 МиБ отправленного в кольцевом
  буфере и умеет отдать его заново с точной позиции (`/t/down?from=`), а
  клиент сам переподключается (до 8 раз, с нарастающей паузой) и продолжает
  ровно с того места, где оборвалось — без потери и без задвоения байт.
  Если нужный диапазон уже вытеснен буфером (клиент отставал слишком долго),
  сервер честно отвечает, что резюме невозможно, вместо того чтобы тихо
  отдать не то. Отдельно: чанк, отправленный вверх, при сетевой ошибке или
  5xx/429 повторяется тем же номером (до 4 раз) — сервер принимает повтор
  идемпотентно; на 4xx-ошибках протокола (испорченные данные, лимиты) клиент
  не повторяет и сразу сообщает об ошибке.
- Половинное закрытие: когда локальное приложение закончило слать (например,
  дочитало HTTP-запрос), сервер закрывает запись в целевое соединение (TCP
  FIN), не трогая чтение — цель может успеть ответить, и это не обрывает
  получение ответа. Под сквозным шифрованием сам факт «вверх больше ничего
  не будет» подписан тем же ключом, что и данные: подделать его или снять с
  чужого запроса, не зная ключа, нельзя.
- Полноценный мультиплекс многих логических стримов в одной HTTP/2-сессии
  (вместо отдельного X25519-рукопожатия на каждое TCP-соединение SOCKS) в
  протокол пока не входит — это отдельная, более крупная переделка формата
  кадров, а не улучшение поверх текущего транспорта.

## Android-приложение
По умолчанию весь трафик телефона идёт через туннель (`VpnService` + tun2socks →
локальный SOCKS5 → CDN), но это настраивается — см. «Приложения в туннеле» ниже.
Готовый APK — в [Releases](../../releases), подробности сборки и внутренностей —
в [`android/README.md`](android/README.md). Проверено на Android 14 (arm64).

**Вкладки**

- **Туннель** — поле `cdn://…` с кнопками «Импортировать» / «Из буфера», строка
  с текущим сервером, кнопка **«Приложения в туннеле»** и кнопка запуска. Всё
  остальное (IP, Host, мастер-ключ, порт, conns, транспорт, метод, UDP, DNS,
  MTU, Fast Open) — в свёрнутой «Ручной настройке», там же «Стереть все
  настройки». Ссылку можно просто открыть из мессенджера: приложение ловит
  схему `cdn://`.
- **Приложения в туннеле** — три режима: «Все» (как раньше), «Только выбранные»
  (в VPN идут только отмеченные приложения, у остальных обычный интернет) и
  «Кроме выбранных» (наоборот). Список — установленные запускаемые приложения
  с иконкой и поиском; выбор действует со следующего запуска VPN. Свой трафик
  клиента к CDN всегда идёт в обход туннеля независимо от режима.
- **Сервер** — автодеплой на VPS по SSH (systemd, автозапуск при ребуте),
  мастер-ключ, `-addr`, метод, периодический рестарт; кнопки «Развернуть»,
  «Статус», «Удалить с сервера» и **«Управление сервером»**.
- **Трафик** — ↓/↑ (всего и скорость), UDP, соединения, пинг и журнал.

**Управление сервером** (панель владельца, ходит к серверу по SSH): аптайм,
сколько ссылок на линии, трафик сервера и список **всех выпущенных ссылок** —
даже неиспользованных — с подписью, состоянием (на линии / привязана /
не использована / отозвана), устройством, адресом и трафиком каждой. Действия по
каждой ссылке: поделиться, сбросить с линии, отвязать, отозвать/вернуть,
удалить. Плюс перезапуск и обновление сервера.

Если приложение пишет, что сервер устарел, — нажмите «Обновить сервер»: реестр
ссылок появился в серверной части версии 2.0.

Приложение не содержит никаких зашитых адресов, доменов и паролей: после
установки все поля пусты.

## Сборка из исходников
```bash
go build -o tunnel .
```

Android-приложение (Go-бинари пересобираются автоматически, см. `android/build-go.sh`):
```bash
source ~/android-dev/env.sh        # JDK17 + SDK + gradle + platform-tools
cd android && gradle :app:assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

## Тесты
```bash
go test -race .   # SOCKS end-to-end во всех транспортах, целостность 4 МБ
                  # и доступ по ссылкам: удаление, отзыв, привязка, панель
```
